# Troubleshooting

**English** | [Polski](PROBLEMY.pl.md)

| Symptom | What to check |
|---|---|
| `WARNING: no reply from receiver` in the sender log | the PC's IP, Windows Firewall (UDP 5005), whether `key` is the same on both sides |
| High ping / spikes in the receiver window | Wi-Fi on the sender (a cable is best - Ethernet; for a phone through a USB hub, then `nmcli radio wifi off`); sender not running as root - log `Low latency: ... run with doas` (the sender's CPU goes into deep sleep) |
| Large "Bluetooth (above minimum)" on the pad card (a few ms or more) | the sender's built-in radio queues reports (e.g. phone: ~10 ms, USB dongle: ~1 ms). Plug in a USB Bluetooth dongle - the sender picks it by itself and turns off the built-in one (Bluetooth panel → Controller: Auto or "Use" next to the dongle; log `Bluetooth adapter (auto): hciN ... (USB)`), then pair the pads with the dongle. Realtek dongles (e.g. TP-Link UB500) need firmware: Alpine / postmarketOS `apk add linux-firmware-rtl_bt`, Debian / Raspberry Pi OS `apt install firmware-realtek`, Arch `pacman -S linux-firmware-realtek` (older: `linux-firmware`) - without it `dmesg` shows `RTL: firmware file ... not found`. Also check the distance and obstacles between the pad and the sender |
| Bluetooth panel: pads disappeared after plugging in / removing a dongle | each controller has its own address - pair the pads with the one the sender uses (panel: the controller marked "in use"). Don't want changes: "Use" next to the built-in one, or Manual (`bt_adapter` in `sender.toml`) |
| Gyro turns the wrong way | editor → Gyro aim → "Invert horizontal / vertical" |
| Crosshair / camera slowly drifts by itself | Test view → gyro chart with the pad lying still; if it isn't flat - "Calibrate gyro" |
| Character walks by itself / camera spins (stick) | Test view → "Measure drift" → "Apply" (drift correction for this pad) |
| Can't push a stick all the way (overlay, weak hand) | Accessibility tab (right column) → "Adjust to the hand", or set the range slider by hand |
| Motion inverted in an emulator (DSU) | `acc_sign` / `gyro_sign` in the receiver config |
| Emulator on another device doesn't see the DSU server | since the security review it listens only on this PC: `dsu_bind = "0.0.0.0"` in `receiver.toml` |
| Pads stop working after going back to an older version (with `key`) | delete `auth.json` next to the newer side (protocol v3 is remembered there) |
| A game profile doesn't activate | games with anti-cheat may block reading the process name; switch manually with PS + d-pad |
| `virtual pad error ... ViGEmBus` | install the ViGEmBus driver or HIDMaestro (README) |
| Settings → Pads: "HIDMaestro not used" | "not found" = HIDMaestro hasn't downloaded yet (Settings → Pads → "Check now"; the download error is shown below it) or a wrong custom path; "administrator rights required" = UAC prompt declined at start - "Restart as administrator" (autostart elevates by itself, event log: "Autostart set to administrator rights"); "pythonnet not installed" = `pip install pythonnet`; ".NET 10 runtime not installed" = the "Install .NET 10" button (winget) or install .NET 10 Runtime manually; "cannot load its types: …" = a file is missing next to `HIDMaestro.Core.dll` (name in the message) - with a custom DLL path copy it from the HIDMaestro zip, or leave the path empty (automatic download); another error while creating = this pad goes through ViGEmBus, details in the event log |
| Event log: `tworzenie pada: HMResourceInUseException ...` / `HMDriverVersionException ...` (HIDMaestro 2.0) | the message names the cause: another program (or a second receiver) holds the pad's index or identity - close it; a driver mismatch or a missing driver payload - restart the receiver (the first start after a HIDMaestro update reinstalls the driver once, which takes a few seconds). Any program still built on HIDMaestro 1.x removes every HIDMaestro device on the machine (2.0 ones too) at its start - all programs on the machine must be on 2.0. If a profile is refused, "HIDMaestro has no 'dualsense' profile (refused: file: JSON path: reason)" shows why. This pad goes through ViGEmBus until it is fixed |
| Event log: `game haptics … composite pad failed` | the pad was created without haptics (it works as before). The message names the cause: usbip-win2 refused (administrator rights / driver install), an old HIDMaestro without the `dualsense-composite` profile, or an unsupported audio format. No new attempt for 10 minutes or until you change the Haptics setting; turning the option off removes the need for the driver |
| UAC prompt on every start | the `DualSenseBridgeAdmin` task is created by a receiver running as administrator - approve UAC once; an account without administrator rights always asks (or `--no-elevate` and ViGEmBus) |
| Pad 2 is player 1 | Settings → Pads → "Fixed player order" turned on; the sender remembers which physical pad is pad 1 (`sender/slots.json` - delete the entry to have the slot assigned again) |
| The pad doesn't rumble | pad card: "old sender" = update the sender (Update in the window), "no permission" = the sender isn't running as root (`sudo` / `doas` or the service from `install-service.sh`), "missing in kernel" = the sender's kernel lacks `CONFIG_PLAYSTATION_FF` and `CONFIG_HIDRAW`, "pad not found" = no `/dev/hidraw` for this pad; on the sender: `sudo python3 sender_rumble.py --test` (rumbles each way in turn, no network) and set `rumble` in `sender.toml` to the one that works; sender log `rumble via ...` and `rumble N/N from PC` (whether the command from the PC arrives); the "Rumble" button on the pad card |
| Wake-on-LAN doesn't wake the PC | red flash = the sender doesn't know the MAC (Settings → Wake-on-LAN: enter it, or start the PC once with the sender running); white flash but the PC sleeps = WoL disabled in BIOS / the network card driver, a Wi-Fi card, or Windows "Fast startup" (turn it off for WoL from full shutdown); sender log `Wake-on-LAN ... -> ...` |
| Console mode only kicks in ~a minute after the PC starts | event log: "Receiver started N s after Windows start" - a large N = old autostart from the Run entry (Windows delays it); the receiver moves it to Task Scheduler by itself (entry in the event log), manually: `python receiver_controller.py --autostart on`. "Console mode waits - X is in the foreground" = program X is not on the list in Settings → Console mode |
| Console mode doesn't react | receiver log: `Console: double ... on controller N` = detected; `only the master pad can do that` = feature reserved for the master (Settings → Master) |
| Bluetooth panel: grey dot / "no data" | sender offline or older than v10 - Update |
| Bluetooth panel: red dot | description in the tooltip: "no permission" = the sender isn't running as root, "bluetooth service not running" = `sudo systemctl enable --now bluetooth`, "no busctl" = system without systemd, "blocked (rfkill)" = `sudo rfkill unblock bluetooth` |
| Pair: "pairing rejected" / "no answer from the device" | the pad is not in pairing mode (Create + PS until the lightbar blinks fast) - turn it on and run the scan again; pad previously paired with a console: Forget, then Pair |
| Pad paired, but it isn't P2, and when turned on with PS it blinks for a few seconds and goes dark | BlueZ didn't store the key (adapter without `Pairable`) or the pad wasn't trusted. The sender now sets trust by itself; a pad without a key is forgotten - put it in pairing mode (Create + PS), run the scan and Pair again |
| A co-op game sees the pads oddly (Steam) | Steam → library → game → Properties → Controller: try "Disable Steam Input" (the game reads two DS4s itself) or the other way round; player order in Big Picture → Settings → Controller |
